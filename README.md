# Project FORESIGHT: Demand & Inventory Intelligence

Weekly SKU-level demand forecasting and stockout / overstock early warning for **NorthBay Living**, a D2C home & lifestyle brand. Built as a Zidio Development data-science engagement.

**Live dashboard:** https://foresightfornorthbay.streamlit.app/  
**Live scoring service:** https://foresight-scoring.onrender.com (interactive docs at [/docs](https://foresight-scoring.onrender.com/docs), health check at [/health](https://foresight-scoring.onrender.com/health))

---

## 1. The problem

NorthBay plans stock on gut feel and spreadsheets. It loses money both ways: best-sellers run out (lost sales) and slow movers pile up (cash locked, later marked down). The Head of Operations asked for four things:

1. How much each product will sell over the next few weeks → **weekly SKU forecast, 8-week horizon**
2. Which products are about to run out → **stockout risk + reorder list**
3. Which are overstocked → **overstock risk + markdown list**
4. Something the team can use without a data scientist → **dashboard + scoring service + plain-language readout**

## 2. Results

**Backtest: rolling origin, 10 folds, 8 weeks ahead each, 4,000 SKU-week forecasts**

| Metric | FORESIGHT (LightGBM) | Seasonal-naive baseline |
|---|---|---|
| **WAPE** (primary) | **8.7%** | 10.5% |
| Bias | −0.9% | +0.3% |
| MAPE (secondary) | 10.5% | 13.3% |
| Folds won | **10 / 10** | – |

The model is **17.6% more accurate** than "same week last year" and wins every fold.

**Hold-out after the stock date:** the 4 weeks from 1 Dec 2025 were never used for training or model choice. On those weeks the model scores 8.7% WAPE against 12.4% for the baseline.

## 3. Quick start

```bash

python -m venv .venv && source .venv/bin/activate       # Python 3.11

python run_pipeline.py                 # raw extracts -> every output (about 1 minute, deterministic)
```

`make run`, `make dashboard`, `make api` and `make test` do the same.

## 4. Data

Four client extracts in `data/raw/`, kept exactly as delivered:

| File | Grain | Notes |
|---|---|---|
| `sales_daily.csv` | SKU × day, 1 Jan 2024 – 31 Dec 2025 | 36,550 rows, 50 SKUs |
| `sku_master.csv.xlsx` | SKU | actually an Excel file; cost column is named `wfr` |
| `calendar.csv.xlsx` | day | actually an Excel file; holidays and promotion events |
| `inventory_snapshots.csv` | SKU × month (1st) | 200 SKUs, 24 snapshots |

### Data-quality issues found and handled (all in code; full log in `outputs/data_quality_log.csv`)

| Issue | Handling |
|---|---|
| Cost column labelled `wfr` | Verified `price − wfr = margin` for 50/50 rows, then renamed `unit_cost` |
| 16 SKUs with unit cost above selling price | Kept and flagged `negative_margin`; Finance to confirm |
| Category/subcategory pairs inconsistent (e.g. Kitchen › Cushion) | Group by category only; subcategory flagged unreliable |
| 3,393 sales rows (21 SKUs) dated before `launch_date` | Sales kept; launch date treated as unreliable (effective launch = first sale) |
| Calendar `week` column not a standard week number | Rebuilt Monday–Sunday weeks from the date |
| 150 SKUs (SKU051–SKU200) in inventory with no sales or master record | Excluded from scoring and reported |
| `Inventory_Value` ≠ stock × cost (0.05×–15×) | Recomputed as `on_hand × unit_cost` |
| Monthly snapshots don't roll forward from sales | Risk scored from the latest snapshot as-is, no projection |
| Partial final week (29–31 Dec 2025) | Dropped from the weekly panel |
| Missing values, duplicates, negative units, revenue ≠ units × price | Checked on every run; none found in these extracts |

## 5. Method

**Frame.** Target: weekly units per SKU (Mon–Sun). Horizon: 8 weeks. Metric: WAPE, with bias as a secondary check. Baseline: seasonal-naive (same week last year).

**Model.** One global LightGBM model covers all SKUs and forecasts each horizon directly (one row per SKU × origin × horizon). Features:
- lags 0–3
- rolling means over 4, 8, 13 and 26 weeks, and 8-week volatility
- expanding mean
- same week last year (raw, smoothed, and level-adjusted), plus a year-on-year level ratio
- planned promotion and holiday days in the target week, and last year's promotion days
- week of year, month, category, price

Demand features and the target are scaled by the SKU's 13-week level. The loss is L1, weighted by that level, which is equivalent to minimising WAPE.

**No leakage.** Every demand feature uses weeks ≤ origin only. The only facts about the target week are calendar facts known in advance. `tests/test_core.py::test_features_do_not_see_the_future` scrambles all future demand and asserts that no feature changes.

**Backtest.** Rolling origin: 10 origins, 4 weeks apart (Jan–Sep 2025). Each fold trains on weeks ≤ origin and forecasts the next 8 weeks.

**Uncertainty.** The 80% range is the empirical 10th–90th percentile of actual ÷ forecast in the backtest, at each horizon.

**Risk rule** (`src/risk.py`, fully transparent):
- *Stockout risk* = P(lead-time demand > on-hand + on-order − safety stock). Flagged above **10%**, i.e. a 90% service level.
- *Overstock risk* = P(8-week demand < on-hand − safety stock). Flagged above **50%**.
- Demand uncertainty is the backtest error spread for that window length, scaled by the SKU's own backtest reliability (normal approximation).
- The two flags give the four quadrants of the Section 08 grid: Reorder now, Markdown / clear, Watch / volatile, Healthy.
- *Sales at risk* = (8-week demand − on-hand − on-order)⁺ × selling price.
- *Cash locked* = (on-hand − safety stock − 8-week demand)⁺ × unit cost.
- *Suggested order* = 8-week demand + safety stock − on-hand − on-order. This is a recommendation only.

## 6. Key assumptions

- The extracts represent NorthBay's real behaviour. Lead times and safety stock in the snapshot are broadly right.
- **Stock position = latest snapshot (1 Dec 2025).** The forecast starts that week so stock and demand line up. December actuals are used only as a live check.
- Promotions after the supplied calendar follow the pattern seen in both years (weekends in Mar/Jun/Sep/Nov). Fixed-date holidays repeat. A no-promotion forecast is also output (`forecast_no_promo`).
- Unit cost = the `wfr` column.
- A 90% service level is the stockout threshold. Change `SERVICE_LEVEL` in `src/risk.py` if the client prefers another.

## 8. Dashboard (D5)

- **Filters:** category pills and a status switch (all, needs action, healthy) at the top. Every figure on the page follows them.
- **Action lists:** prioritised reorder and markdown tables. Click any row to open that product. Each list downloads as CSV.
- **Product detail:**
  - forecast vs actual with the 80% range, past backtest forecasts and a forecast without promotions
  - adjustable history window and range slider
  - a **what-if panel**: change units on hand, on order, lead time or safety stock and the risk, action and rupees recalculate live, using the same rule as the pipeline
- **Risk map:** every product on the stockout-vs-overstock grid. Click a bubble to open it.
- **Forecast accuracy:** model vs baseline by test window or by weeks ahead, with a plain-language explanation of the flags.

## 9. Scoring service (D6)

| Endpoint | Purpose |
|---|---|
| `GET /health` | status |
| `GET /skus` | valid SKU ids |
| `GET /score/{sku_id}` | 8-week forecast (with 80% range and a no-promo version) + risk, action, rupees at stake |
| `POST /score` | batch of up to 200; optional fresher stock per SKU is re-scored with the same rule |

```bash
curl https://<service-url>/score/SKU012
curl -X POST https://<service-url>/score -H "Content-Type: application/json" \
     -d '{"items":[{"sku_id":"SKU012","on_hand_units":900},{"sku_id":"SKU025"}]}'
```

Bad input doesn't crash the service:
- an unknown SKU returns **404**, or a per-item entry in `errors` for a batch
- negative, non-numeric or empty input returns **422** with a readable message
- missing model outputs return **503** with instructions

## 10. Deployment

Both apps read the seeded outputs committed in `outputs/`. Re-run the pipeline and push to refresh them.

- **Dashboard → Streamlit Community Cloud:** New app → this repo → main file `app/dashboard.py`. It installs `app/requirements.txt`.
- **Scoring service → Render:** New → Blueprint → this repo. `render.yaml` builds from `service/requirements.txt` and runs `uvicorn service.main:app`. Health check: `/health`.

## 11. Scope

Built exactly to the brief: D1–D7, weekly SKU forecast over a defined horizon, risk scoring, one pipeline, a dashboard, a scoring service and a readout.

**Not built (out of scope per Section 4.3):**
- live integrations with client systems
- price optimisation, supplier selection or inventory-optimisation solvers
- real-time or streaming infrastructure
- any automated purchase-order placement

The optional stretch goals in 11.1 were not attempted.

**Repository visibility:** public, which Section 13 of the brief allows. The four raw extracts are simulated data and are included so anyone can re-run the pipeline end to end.
